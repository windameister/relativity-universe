# 路线图与下一步

先修当前原型里已经暴露、而且会挡住「每局都是不同故事」的问题，再谈正式版的架构。下面关于引擎和渲染的部分是建议，由发起人决定。

## A. 当前原型上应先治的问题

这是事件库第一阶段交付时列出的优先项，建议按这个顺序做。做完应能用 `node tools/evcheck.js` 和一次玩家视角试玩复核。

### A1. 宗教线不要走成同一条阶梯（优先）

现状：约 99% 的神眷文明都能走到中段，路线却大多一样，很少出现改革派（`rel.reformation`）和使者号（`rel.envoy` / `rel.envoy_meet`）。

建议：

- 用 `evcheck` 和 `playtest/r6_faith_stats.js` 看清各节点的实际到达率，对过高的中段事件降权，对改革 / 使者 / 伪先知 / 圣战等分支按稳定度、战争、回访次数、神↔恶魔转换加权重
- 前一阶段的具体细节要被后续文本引用（例如已经出现过「驱魔节」，使者号船员应还戴着同样的面具）
- 给玩家深度投入的神眷文明留出预警或短暂保护期，避免「刚扮完神，对方转头被随机光粒抹掉、整条线归零」。保护不能变成无敌，但要让玩家有机会警告或撤离

### A2. 大事件卡片减量、提高分量

现状：平均每局约 6 张卡，一份到访报告里有时叠 4–5 张，冲击被冲淡。覆盖率测试里 `card.helped_extinct` 最常见（300 局 352 次，单局最多 10 次），是优先要节制的对象。

建议：

- 导演配额：同一份报告最多 1–2 张卡；同一次到访只保留因果最重的那张
- 过期、重复、信息量低于日志的卡不要弹（过期预警已在 r6 修过，需防止回潮）
- 母星被压平、盟友灭绝、归零者广播这类，应少而重，并在 3D 回放里单独减速演出

### A3. 让从未触发的事件真的能发生

整理本仓库时用当前代码重跑 `node tools/evcheck.js --n 300`（5 种玩法 × 60 个种子，每局 12 站再推 500 年），仍有 10 个事件一次都没出现：

`ally.mediate`，`recog.demand`，`recog.give_maps`，`recog.refuse`，`rel.god_to_devil`，`rel.answer_silence`，`rel.keep_faith`，`rel.endorse`，`warn.evacuate`，`warn.evac_go`。

同一次检查还列出 13 种「写入后没有事件再读取」的终点史实：`echo_gs2`、`echo_gl3`、`mediated`、`mediate_failed`、`questioned`、`sided`、`refugee_bcast`、`refugee_spurned`、`reparation`、`fleet_met`、`faith_martyr`、`faith_blessed`、`warned`。

建议：

- 改权重或条件之前，先再跑一遍 `evcheck`，不要只凭这份名单
- 检查是条件过严、前置事件太稀有，还是玩家选项根本走不到（调停和撤离尤其像是「设计上应该能见到」的）
- 对「值得存在但极稀有」的事件，应在报告里标明是故意稀有；对应该能见到的，放宽前置或加一条更常见的入口
- 给那 13 种终点史实补后续，或明确它们只是记录、不必再被读取。`mediated` 没有人读，会让「调停成功」即使做出来也没有下文

### A4. 再确认光粒重复命中

第 5 轮统计里，「同一星系被光粒击中 ≥ 2 次」曾降到 0。交付时仍把它列为观察项。复修 A1–A3 时，用 `test_sim.js` 和 `curse_stats.js` 再跑一遍，确认死寂 / 已压平的星系不会再被打。

## B. 下一轮玩法（原型上就可以做）

事件库交付时的原话是：先治上面三处，再做补给经济和 3D 回放的节奏。

### B1. 补给与成长经济

现在补给几乎没有压力（试玩中最低约 75），地球殖民地都能「母星回家」补满并送科技，回家睡觉比拾荒、考古更优。

建议方向（第二轮试玩已提出，仍有效）：

- 只有太阳 / 地球文明的母星本体回家才补满并送科技；殖民地只给少量补给，送科技要有冷却
- 考古、拾荒的收益与遗迹峰值科技挂钩，允许超过飞船当前科技
- 曲率启动和长途航行的补给消耗可以保留，但要让玩家有时必须停靠、交易或冒险拾荒，而不是永远满仓
- 冬眠已有寿命和事故，不要再变回免费时光机

### B2. 3D 回放节奏与演出

已经值得看的部分（二向箔咬合扩张、光粒冲击、曲率尾迹）应保留。要改的是：

- 没有事件的空白年代不要放 4–5 秒「暂时风平浪静」；给跳过、倍速，或把空档压到一眼能扫过
- 归零者广播、母星压平、盟友灭亡，必须减速并单独给画面（归零者广播在 r6 已加，需在真机上确认观感）
- 回放要么遵守光延迟，要么明确标成「上帝视角回放」并允许关闭——现在「不计光延迟」和游戏核心规则是打架的
- 二维化不要长期停在「彩色半透明球」。目标是让人读出「三维空间正在跌落成一幅画」
- 标签重叠、默认镜头过近导致远处的星点不到，属于可读性，应一并处理

### B3. 事件库后续阶段（设计稿里的 P2–P5）

P1 只迁了回响、后代和大事件卡。仍在模拟代码里手写文本和离散规则的，包括危机改名、日常外交战争、目击闪光后的反应、流亡去向、接触选项本身。见设计稿第 9 节。

不建议在 A、B 还没稳住之前，把 P3 / P4 整段重写一遍。可以先补内容和导演层（P2、P5 的一部分），再视正式版架构决定是否继续迁移。

### B4. 其他仍有价值、但不必插队的想法

- 提高中后期新智慧物种的诞生率，或与二维化 / 黑域留下的空白区挂钩，避免传教和探索在中盘断粮
- 考古应根据废墟主人的历史生成不同发现（是不是你的信徒、死于谁）
- 被你得罪的两个文明结成同盟、联合追捕
- 母星被压平后，「最后的地球人」身份和地球流亡舰队找你
- 名字生成再拉开差异，避免埃汐 / 埃岚这种难以分辨的名字
- 给长局一个可选择的终局目标：逃离归零、加入黑域、找到歌者、让地球活到某个纪元

## C. 正式版：建议架构（请发起人拍板）

目标不是把现在的单文件 HTML 无限堆上去，而是做成「可以认真玩、画面配得上这个宇宙」的一版。下面是建议，不是已经决定的方案。

### C1. 必须守住的边界

- 确定性模拟内核与渲染分离。同一种子、同一串操作，在无界面测试和带画面的游戏里应得到同一部宇宙史
- 第 2 节物理硬规则不能为了视觉效果让步：不超光速、洛伦兹时间膨胀、常规推进接近不了 c、光延迟
- 事件继续作为数据，不要回到在渲染层写剧情
- 先能在本机跑，再谈发行平台

### C2. 推荐的分层

```
规则与内容         事件 JSON / 文本 / 数值表
        ↓
模拟内核（纯逻辑）  生成宇宙、逐年演化、航行、光延迟、史实、事件解释器
        ↓
表现适配           把某一时刻的可见状态（含光延迟）交给渲染和 UI
        ↓
渲染与交互         3D 场景、回放、UI、音效、输入
```

模拟内核应能在 Node（或同等无界面环境）单独跑测试、回放和统计，不引用渲染库。当前 `SIM` 已经接近这个形状，正式版值得把它从 HTML 里拆成真正的模块，而不是继续在 `index.html` 的 `<script id="sim">` 里生长。

### C3. 引擎选项

没有唯一正确答案，取决于发起人更想要「尽快在网页里做出震撼画面」，还是「做一个可长期迭代的本地游戏」。

| 方案 | 优点 | 代价 | 适用 |
|---|---|---|---|
| A. 继续 Web：把现在的 Three.js（或改 WebGPU）做深 | 现有模拟和事件库可几乎原样搬走；试玩成本低；易分享 | 单文件已经约 1MB+ 逻辑，继续堆会难维护；顶级电影级画面有上限 | 想尽快做「能发给别人玩的震撼网页版」 |
| B. Godot（3D）+ 内核用 GDScript / C# 重写或用 WASM 挂上现有 JS/TS 内核 | 场景、特效、发行管线成熟；适合单机体验 | 要做一层绑定；需决定内核是否迁移出 JS | 想要桌面端、更好的工具链，又不想从零写引擎 |
| C. 自研或 Bevy / Unity 等 | 渲染上限高，适合把二维化做成真正的空间效果 | 工期明显更长，和现有原型距离最大 | 只在画面被定成最高优先级、且接受更长周期时考虑 |

更稳的路径可能是：**先把 JS/TS 内核模块化并补测试（方案 A 的工程清理），同时用它驱动一个更强的渲染层；** 若网页渲染到顶，再把同一份内核接到 Godot 或其它引擎，而不要两边各写一套宇宙。

### C4. 渲染目标（正式版应追求的感觉）

现有 3D 是「能说明问题的宇宙示意图 + 若干漂亮特效」。正式版应往这些方向靠：

- 银河：有远近层次的星场、尘埃带和星云，而不是平坦的点子加一层贴图
- 恒星：按光谱型能分辨，黑洞、中子星、白矮星各有各的读法
- 曲率航行：接近 c 的光学效果要服从相对论直觉（光行差、蓝移 / 红移可以 stylized，但不能看起来像瞬移）
- 光粒：远方一个几乎不移动的亮点，然后在极短时间内压过来，命中时有冲击壳和星芒
- 二向箔：命中点附近的三维结构被「熨平」，前沿以光速推进，被吞没处变成可凝视的二维画面，而不是一个彩色泡泡
- 黑域：从外面看是吞掉光线的洞，不是普通的黑球贴图
- 回放：事件处有镜头和光线的变化，空白处可压缩；可选「我当时能看到的」和「上帝视角」

视觉可以 stylized，但空间关系、速度和因果要跟模拟一致。

### C5. 建议不要一上来就做的事

- 不要先重写物理或「优化」掉光延迟
- 不要在没有模块化内核之前，把项目搬进一个全新引擎并同时改玩法
- 不要把事件库改回硬编码剧情
- 不要为了丰富银河而把上亿恒星都做成活文明——保持「可交互的世界是稀疏的，背景是宏大的」

### C6. 高光场景：从地球仰望二向箔吞没太阳系

发起人点名想看的一个场景，适合做成正式版的第一个「电影级」演出，也可以单独做成技术 demo 或宣传片。

**画面：**镜头在地球地表，看着远处的行星依次被二维化，平面在天空里越铺越大，最后吞到地球。

**分段：**

1. **前兆：**夜空正常，外侧某颗行星（建议木星或海王星）的亮度和形状开始异常，望远镜式的特写里能看到它一侧被「熨平」。
2. **展开：**行星从接触面开始压向平面，压的同时表面细节在平面上按面积摊开、无限延展，变成巨大而极薄的彩色画面；土星环摊成一圈圈同心条纹。
3. **推进：**二维化波前由外向内推进，按到太阳的距离依次吞掉各颗行星。时间轴可以用真实光速（各行星间隔几十分钟到几小时），回放时压缩空白，到事件时放慢。
4. **太阳：**太阳被压进平面，化成一片发光的二维画面，天空的光照和颜色随之剧变。
5. **地球视角终局：**平面横跨整个天空，大气散射、地平线和地面的光影都跟着变；最后波前触到地球，镜头本身被压平，切到「平面上的地球」。

**技术要点：**

- **压平变换：**在顶点着色器里按「到二维平面的距离」和时间插值，把顶点投到平面上；投影时按距离放大展开，避免压成一张单薄贴图。
- **波前：**用一个随时间推进的球面或平面作前沿，前沿以内的物体进入二维化状态；和模拟里的二向箔推进参数保持一致。
- **尺度：**真实比例下从地球看行星只是光点，需要允许「望远镜特写」或艺术放大镜头，并在界面上标明是哪种视角。
- **渲染：**HDR 加色调映射、辉光、体积光、大气散射、粒子碎屑；平面上的画面要有可凝视的细节（可用行星原贴图摊开加程序化纹理）。
- **两种用途：**实时版放进游戏（玩家家园被打击时的演出或回放），离线版可用 Blender 或 Unreal 渲成宣传片。

**验收：**一眼能看出是「立体被压成平面」，而不是爆炸、黑洞或彩色气泡；推进顺序和时间跟模拟一致；从地球视角看有尺度感和压迫感。

## D. 建议的工作顺序

1. 在本仓库的原型上修 A1–A3，必要时核对 A4，保持 `test_sim.js` 与 `evcheck` 全绿
2. 做 B1 补给经济和 B2 回放节奏，让现有 3D 更好玩、更好看
3. 把模拟内核从 HTML 里拆成独立模块，补一层对「可见状态」的接口
4. 发起人选择渲染方案（加深 Web，或接 Godot 等），再冲击更逼真的打击与银河表现；可先拿 C6「二向箔吞没太阳系」做第一个高光场景
5. 按设计稿推进事件库 P2–P5，把每局差异做得更明显

如果只能做一件事：先让宗教分叉和稀有事件真正出现，并压住叠在一起的卡片。故事一旦稳定，渲染才有值得被拍漂亮的瞬间。
